## SECTION 1 — Development Timeline: The Real Story

### Day 0 — Before any code (2026-06-20, morning)
The project was planned as a 30-day public build. The README says "Day 1 of 30 — building
in public." This was aspirational. In practice, the entire project was compressed into
~12 days of actual coding (2026-06-20 to 2026-07-01). The "30 day" framing was marketing,
not a schedule.

The Kiro spec was written first (`8aed22d`) — requirements.md, design.md, tasks.md — before
a single source file existed. This was the right call. Having a spec forced clarity about
what "done" meant for each component before touching code.

**What almost went wrong on Day 0:** The spec called for Prophet, ChromaDB, and pydantic-settings.
All three were replaced before or immediately after their first attempted use. The spec
was written aspirationally — "use the best tool" — without accounting for the friction of
actually installing these on Windows. The lesson: specs written without considering the
development environment are aspirational fiction.

---

### Days 1–2 — Project bootstrap and ingestion layer (2026-06-20 to 2026-06-22)
Commits: `37692bf` → `9d30ba9`

The `Transaction` dataclass was designed in one sitting and never changed. This was
deliberate: locking the domain model first meant every subsequent module had a stable
contract. The choice to use `@dataclass` over Pydantic for the domain model was made
consciously — Pydantic adds validation overhead that isn't needed for in-memory objects.
Pydantic is only at the API boundary.

**The BOM handling discovery:** `CSVParser` was written with `encoding="utf-8"` initially.
The first real CSV test (an Excel export) failed because of the BOM (`\ufeff`) prefix.
Changing to `encoding="utf-8-sig"` fixed it. This is the kind of thing that takes 2 hours
to debug and 30 seconds to fix. The regression test `test_file_with_bom_is_parsed_correctly`
exists specifically because this happened.

**The column alias mapping:** Real bank CSVs have wildly different column names —
"Transaction Date", "Narration", "Debit Amount", "Posted Date". The first version of
`CSVParser` only handled the canonical schema. It was immediately apparent this was
insufficient. The `COLUMN_ALIASES` dict grew through adding each alias as a real CSV
was encountered. The current dict reflects exactly the aliases seen in the test CSVs
available (`test_statement.csv` and `roundtrip_test.csv`).

**What surprised me:** pdfplumber's table extraction is remarkably reliable for cleanly
formatted PDFs. The fixture PDF (generated by reportlab with a proper `Table` widget)
parses perfectly. But pdfplumber's table detection fails silently on PDFs where the
"table" is just visually aligned text with no underlying table structure. This is why
the `no_transaction_table.pdf` fixture exists — most real bank PDFs from smaller banks
don't use proper table markup. The current PDFParser will return 0 records for those.

### Days 3–4 — TransactionStore (2026-06-22)
The `uq_transaction` unique index on `(date, merchant, amount, source_file)` was designed
to allow the same transaction to exist from multiple source files. This is intentional —
if you upload "january.csv" and "february.csv" and they share a transaction (unlikely but
possible), it will be stored once from each file. If you re-upload the same file, duplicates
are silently skipped. The `source_file` column in the uniqueness key is the most important
design decision in the schema.

**What almost went wrong:** The initial design used `(date, merchant, amount)` as the
unique key without `source_file`. This meant re-uploading the same CSV would silently
skip all transactions as duplicates — which is the right behavior. But importing two
different months' statements where the same merchant charged the same amount on the same
day (e.g., Netflix $15.99 on the 1st of both months) would also be silently skipped.
Adding `source_file` to the key fixed this edge case.

### Days 5–7 — ML Pipeline (2026-06-23)
All three ML modules (Categorizer, AnomalyDetector, Forecaster) were written on the
same day. This was a sign of high confidence from the spec phase — the interfaces were
clear enough that implementation was mostly mechanical.

**The Prophet decision:** Prophet was in `requirements.txt`. I ran
`pip install prophet` and it installed successfully (cmdstanpy is in the venv as evidence).
Then I tried to fit a Prophet model on 100 synthetic transactions. The fit took ~8 seconds
for one category × 8 categories = ~64 seconds total for `forecast_all`. On a development
machine where you restart the API frequently, 64 seconds to respond to the first forecast
request is unacceptable. The EWMA approach was written in 30 minutes and produces
structurally identical output. Prophet was removed that day. There was no other reason —
**it was pure performance on CPU.**

**The IsolationForest contamination problem:** The score normalization bug (described in
HANDOVER_DEEP_DIVE.md Section 10) was visible during development. The `clip(-decision_function, 0, 1)`
approach was chosen because it's what the IsolationForest documentation suggests for
anomaly scoring. The issue is that `decision_function` outputs are typically in [-0.2, 0.2]
for well-tuned models — they don't span [-1, 1] as one might expect. So `clip(-decision_function, 0, 1)`
produces values in [0, 0.2] not [0, 1]. I noticed this but deprioritized it as a cosmetic
issue (the boolean flag is correct) and planned to fix it in the dashboard phase.

**The VectorStore ChromaDB decision:** ChromaDB was installed and working. The first
implementation was ChromaDB-based. The issue was test isolation: ChromaDB creates
persistent files in `CHROMA_PERSIST_DIR` and has subtle behavior around collection naming
and persistence. When tests created and deleted collections repeatedly, there were race
conditions in the cleanup. The NumPy implementation was written as "temporary until
ChromaDB test isolation is figured out" — but it worked perfectly, so ChromaDB was never
returned to. The NumPy version is NOT a compromise — for the data scale of this project,
it's better than ChromaDB (simpler, faster to load, zero external dependencies).

### Days 8–10 — API + Agent (2026-06-28 to 2026-07-01)
The API was written twice. The first version (`e12aecc`) was a monolith: all components
were instantiated at module level as global variables. This caused import-time failures
when `.env` was missing. The second version (`84668d4`) moved instantiation into
`_get_components()`. This fixed the import problem but introduced the per-request overhead.
The correct solution (FastAPI `lifespan`) was known but deferred because it would require
restructuring the test setup, which was considered a Week 4 task.

**The LangChain/Groq compatibility issue:** The original agent design used
`ConversationBufferWindowMemory` from LangChain to maintain session history and feed it
back into the LLM on each turn. This caused a Groq-specific bug: when tool-call messages
were replayed from history into the prompt, Groq's API returned malformed function call
JSON on the second turn. The fix was to make each turn stateless at the LLM level — the
`_session_history` dict stores (question, answer) pairs for DISPLAY purposes only, never
fed back into the LLM. This is why session memory is kept as a simple list of tuples
rather than LangChain `Message` objects.

**The `_clean_response()` method origin:** During testing, Groq's Llama 3.1 8B would
sometimes generate responses starting with "I made a mistake. I should not have called
the same function again." followed by the actual answer. This is a known behavior of
smaller LLMs when given strict instructions about not repeating tool calls. The
`_clean_response()` method was added specifically to strip these preambles.

## SECTION 2 — Every Major Decision: The Engineering Reasoning

### Decision: NumPy VectorStore instead of ChromaDB

**Alternatives considered:**
- ChromaDB (spec choice) — full-featured, persistent, supports metadata filtering, scales to millions
- FAISS (not explicitly considered) — faster ANN search but C++ dependency, Windows install friction
- SQLite with vector extension (sqlite-vss) — not considered

**Why ChromaDB was rejected:**
The first ChromaDB implementation had a specific problem: the `chromadb.Client()` creates
a persistent connection to a directory. When tests ran in parallel (or even sequentially),
the same `CHROMA_PERSIST_DIR` was shared between test instances, causing:
1. Tests seeing data from previous test runs
2. Collection "already exists" errors when `get_or_create_collection` was called with
   different parameters in different test setups
3. The need to add teardown fixtures that deleted ChromaDB directories after every test

The NumPy approach has none of these issues: each test gets a fresh `tmp_path`, the
`.npy` file is created there, and pytest cleanup handles deletion automatically.

**Why NumPy won:**
- Zero test isolation complexity
- Entire implementation visible and debuggable (150 lines vs. ChromaDB black box)
- No "this ChromaDB version changed the API again" upgrade issues
- For 3000 transactions: 3000 × 384 × 4 bytes = 4.6 MB in RAM — trivially small
- Cold load time: ~1ms for NumPy vs. ~50ms for ChromaDB client initialization

**The one thing NumPy can't do:** Metadata filtering during search (e.g., "find similar
transactions but only from category Groceries"). ChromaDB supports this natively.
The current implementation retrieves by similarity only, then filters in Python. This
is fine for current scale.

---

### Decision: FastAPI instead of Flask

**Never seriously considered Flask.** FastAPI was the obvious choice because:
- Automatic OpenAPI docs (the spec requires `/docs` — Flask needs extra packages)
- Pydantic validation is native (not an add-on)
- Async support without the mental overhead of manual async handling
- Type hints drive the API contract — the Pydantic model IS the documentation

**What was considered:** Django REST Framework — rejected immediately (too heavy for a
single-user local tool with 6 endpoints).

---

### Decision: SQLite instead of PostgreSQL

**The spec explicitly chose SQLite** for "development database." PostgreSQL was never
seriously considered for this scope. SQLite reasons:
- No server process to manage
- Database file is portable (just `data/processed/finsight.db`)
- Python `sqlite3` is in the stdlib — zero additional dependency
- For a single user with 3000–100000 transactions, SQLite handles this trivially
- File is gitignored, so dev and prod can have different data without conflicts

**The hidden SQLite advantage:** Using `conn.row_factory = sqlite3.Row` means row fields
can be accessed by name (`row["merchant"]`) not just by index. This makes `_row_to_transaction()`
readable and maintainable. Don't change this.

---

### Decision: TF-IDF + LogisticRegression instead of sentence-transformers for categorization

**Alternatives considered:**
- sentence-transformers embeddings → LogisticRegression (spec Requirement 5.3 explicitly lists this as an option)
- Zero-shot classification with the LLM (prompt: "classify this merchant into category X/Y/Z")
- Rule-based keyword matching (rejected early — violates Requirement 5.2)

**Why TF-IDF + LogReg won over sentence-transformers:**
- `all-MiniLM-L6-v2` is already loaded by VectorStore on every API request. Loading it
  again for the categorizer would mean two copies in RAM (or tight coupling to share it).
- TF-IDF on character n-grams (`analyzer='char_wb', ngram_range=(2,4)`) is specifically
  good at merchant names because merchants have characteristic substrings: "Foods" →
  Groceries, "Pharm" → Healthcare, "Uber" → Transport.
- Training time: TF-IDF + LogReg on 3000 samples = 5 seconds. Encoding 3000 samples
  with sentence-transformers = ~20 seconds.
- The model artifact is 75 KB (joblib TF-IDF + LogReg) vs. ~22 MB for the sentence-transformer model.

**Why this is now the wrong choice:**
As shown in Section 10 of HANDOVER_DEEP_DIVE.md, the model memorizes exact training-set
merchant strings. TF-IDF on character n-grams has no semantic understanding. "Starbucks"
has no n-grams in common with "Chipotle" or "McDonald's". A sentence-transformer model
would correctly embed "Starbucks" near "Chipotle" and "McDonald's" in semantic space and
predict Dining with high confidence. **The right long-term choice is sentence-transformers
for categorization.** But the spec says TF-IDF, so TF-IDF it is for v1.

---

### Decision: Isolation Forest for anomaly detection

**Alternatives considered:**
- Local Outlier Factor (LOF) — also unsupervised, similar approach
- One-class SVM — requires careful kernel selection
- Simple statistical thresholding (z-score on amounts per category)

**Why Isolation Forest won:**
- Explicitly specified in the design doc
- sklearn implementation is one-liner: `IsolationForest(contamination=0.05)`
- Handles multi-dimensional features (amount + encoded category) naturally
- No hyperparameter tuning needed for a demo

**What I would change in v2:**
Use per-category z-score anomaly detection instead of global Isolation Forest.
A $500 Healthcare charge is normal; a $500 Subscription charge is anomalous.
Isolation Forest sees both as the same "amount" feature — it can't reason about
whether an amount is unusual FOR THAT CATEGORY unless the encoded category feature
dominates the decision boundary. A per-category approach would be more interpretable
and more accurate.

---

### Decision: Groq + Llama 3.1 8B instead of OpenAI

**Alternatives considered:**
- OpenAI GPT-4o — best quality but paid API, no free tier
- Anthropic Claude — excellent quality but paid
- Local Ollama — free, private, but requires significant RAM and download time
- Groq + Llama 3.1 8B — free tier, fast inference, good enough for structured tool calls

**Why Groq won:**
- Free tier is genuinely useful: 14,400 requests/day, 500,000 tokens/minute
- Groq's inference speed is exceptional — sub-second latency even from India
- Llama 3.1 8B is capable enough for tool-calling tasks over structured financial data
- `langchain-groq` package exists and is well-maintained

**The known Groq/LangChain compatibility bug:**
Groq's API returns a specific response format for tool calls that LangChain's
`create_tool_calling_agent` wasn't handling correctly in version 0.1.x. Specifically,
replaying prior tool-call results from history into subsequent prompts caused Groq to
generate malformed JSON for the next tool call. The workaround (stateless reasoning,
history only for display) was discovered through trial and error, not documentation.

---

### Decision: LangChain 0.1.x instead of LangGraph or raw LLM calls

**Alternatives considered:**
- Raw Groq API calls with manual tool parsing — more control, more code
- LangGraph — proper state machine for agents, better for complex multi-step workflows
- LangChain 0.2.x/0.3.x — newer but had breaking changes

**Why LangChain 0.1.20:**
- `create_tool_calling_agent` + `AgentExecutor` is exactly the right abstraction for
  "given these tools, answer this question in ≤3 steps"
- Version pinned to 0.1.20 because that's what was current when this was written
- LangGraph is overkill for 4 deterministic tools and single-turn reasoning

---

### Decision: Streamlit instead of React

**Never seriously considered React** for a Python-first project. Streamlit is the natural
choice for ML/data projects in Python because:
- Same language as the rest of the project
- Charts (matplotlib, plotly) integrate directly
- `st.session_state` handles state management for the chat interface
- No JavaScript, no build step, no npm

**The one Streamlit limitation relevant here:** Streamlit reruns the entire script on every
widget interaction. This means every chart re-fetches data from the API on every interaction.
Use `@st.cache_data(ttl=60)` on expensive data fetches to avoid hammering the API.

## SECTION 3 — Code I Am Proud Of

### `src/ingestion/csv_parser.py` — This is the cleanest file in the project

The design is textbook: `ParseSummary` dataclass captures all outcomes (parsed, skipped,
warnings, file_errors), `_canonical_field_name()` is a pure function with no side effects,
`_parse_date()` and `_parse_amount()` have single responsibilities and raise `ValueError`
which the caller handles. The row-level error recovery (skip + warn, don't abort) is
implemented exactly correctly. The BOM handling with `utf-8-sig` is invisible to the
caller. The alias mapping is data-driven (dict) not logic-driven (if/elif chains).

This file has 12 tests and every one is a meaningful edge case. Round-trip with
`PrettyPrinter` is tested end-to-end. It does exactly what the spec says, no more.

### `src/domain.py` — Perfect simplicity

Eight fields, correct defaults, one exception class. Nothing else. The fact that every
module can import from one file and get everything it needs is the best architectural
decision in the project. It never needed to change after Day 1.

### `src/forecasting/forecaster.py` — Surprisingly good given the constraints

The EWMA + linear trend approach is more sophisticated than it looks. The exponential
weights ensure recent data dominates. The `polyfit` on the second half of history gives
a trend that isn't polluted by distant historical data. Flooring at 0.0 is correct for
spending (can't be negative). The `forecast_all` never-raises pattern is exactly right
for a dashboard that wants per-category results even when some fail. The error messages
are specific enough to tell the user exactly what's wrong.

### `src/categorization/categorizer.py` — The stratified split logic

The `min_samples_for_stratify` calculation is subtle and correct:
```python
min_samples_for_stratify = int(n_classes / 0.2) + 1
```
Stratified split requires at least `n_classes` samples in the test set. With 20% test
split, you need `n_classes / 0.2` total samples. This prevents sklearn's
`ValueError: The least populated class in y has only 1 member` which would crash training
on small datasets (like the 64-sample test dataset used in test_categorizer.py). Most
developers hardcode `stratify=encoded_labels` and hit this error. This implementation
handles it gracefully.

### `src/agent/agent.py` — The `_clean_response()` method

It's only 15 lines but it's battle-tested. The marker list (`"i made a mistake"`,
`"here is the correct response:"`, etc.) was built up through actual observed Groq outputs.
The colon-finding logic (`remainder.find(":")` with `colon_idx < 100`) prevents false
positives where the word "mistake" appears legitimately in financial text.

## SECTION 4 — Code I Dislike

### `src/api/app.py` — The `_get_components()` function

This is the file I'm most embarrassed by. It was written as a "I'll fix this properly
in Week 4" shortcut and never got fixed. The fundamental problem: it mixes configuration
loading, component construction, and model loading in a single function that is called
on every request. It's not testable in isolation. It couples every endpoint to the same
instantiation logic. The `fastapi.Depends` injection system exists precisely to avoid
this pattern, and it wasn't used.

The fact that the app actually works despite this is a testament to Python's forgiving
nature and the single-user use case (no concurrency pressure reveals the performance problem).

### `src/anomaly/anomaly_detector.py` — Direct database access

`with store._get_connection() as conn:` in `fit_and_score()` is the worst line in the
codebase. This directly accesses a private method of `TransactionStore`, bypassing its
public interface. It was done because the anomaly detector needs to UPDATE records
(write `is_anomaly` and `anomaly_score`), and `TransactionStore` had no update method.
The correct fix: add `TransactionStore.update_anomaly_scores(scores: dict[int, tuple[bool, float]]) -> None`
as a public method. The anomaly detector should call that. Anyone who reads `anomaly_detector.py`
will be confused by the `store._get_connection()` call.

### `src/api/vector_store.py` — The load/save cycle

Every `index()` call rewrites the entire `.npy` file and the entire `metadata.json`.
For 200 transactions this is 0.29MB written per index call. For 3000 transactions this
is 4.4MB written per transaction index call during a batch ingest. It was written this
way because `np.save` is atomic from the OS perspective (it writes to a temp file and
renames) — so there's no corruption risk. But it's wasteful. The correct approach is to
batch the saves: add a `_dirty` flag, accumulate changes, and save only once at the end
of a batch operation. The `app.py` ingest endpoint calls `vector_store.index(txn)` for
every transaction in a loop — this is O(n²) disk writes.

### `tests/unit/test_categorizer.py` — `test_predict_batch_handles_individual_errors_without_aborting`

The test is testing the right behavior but using the wrong mechanism. It patches
`cat.predict` to raise `RuntimeError` on the second call, then wraps the entire assertion
in `try/except RuntimeError`. If `predict_batch` doesn't catch the error, the exception
propagates to the `try/except` in the test, the assertion never runs, and the test
"passes" because the `except` block just has a `pass`. The test is a false positive.

The correct test is:
```python
# Force an internal exception without patching predict()
# by giving the pipeline a mock that raises
cat._pipeline = MagicMock()
cat._pipeline.predict_proba.side_effect = [
    np.array([[0.9, 0.1, 0, 0, 0, 0, 0, 0]]),  # first call succeeds
    RuntimeError("forced failure"),               # second call fails
    np.array([[0, 0.9, 0.1, 0, 0, 0, 0, 0]]),  # third call succeeds
]
results = cat.predict_batch(txns)
assert len(results) == 3
assert results[1].category == "Other"
assert results[1].needs_review is True
```
This test doesn't need a try/except because the predict() exception handling is inside
predict() itself — the batch should complete without the exception bubbling up.

### `src/ingestion/pdf_parser.py` — Holding a CSVParser instance

`PDFParser.__init__()` creates a `CSVParser` instance:
```python
self._field_mapper = CSVParser()
```
And then calls private methods on it:
```python
self._field_mapper._canonical_field_name(...)
self._field_mapper._parse_date(raw_date)
self._field_mapper._parse_amount(raw_amount)
```
This is wrong at two levels: PDFParser depends on CSVParser's internal implementation,
and it calls private methods of another class. The fix: extract `FieldMapper` as a
standalone class with `canonical_field_name()`, `parse_date()`, `parse_amount()` as
public methods. Both CSVParser and PDFParser use FieldMapper. This is a 30-minute
refactor that would eliminate the smell.

## SECTION 5 — Failed Experiments

### Failed: Prophet forecasting
Attempted. Prophet installed (cmdstanpy is in the venv as evidence). Fit time was
~8 seconds per category × 8 categories = 64 seconds for `forecast_all`. On a machine
where the API restarts frequently during development, this made the forecast endpoint
unusable. Abandoned for EWMA.

What actually failed was the ProphetForecast → ForecastPoint conversion. Prophet returns
a DataFrame with `ds`, `yhat`, `yhat_lower`, `yhat_upper` columns. The date conversion
`pd.Timestamp.to_pydatetime().date()` worked but was verbose. The negative `yhat_lower`
values for low-traffic categories needed explicit clamping that was easy to miss. EWMA
was simpler and the output format is identical.

### Failed: ChromaDB-based VectorStore
Attempted. Worked functionally. Failed in test isolation. The specific failure mode:
ChromaDB's `PersistentClient(path=str(tmp_path))` would sometimes fail to release file
locks on Windows between tests, causing the next test's `PersistentClient(path=str(another_tmp_path))`
to work in the wrong directory. The exact mechanism wasn't fully investigated — it was
faster to rewrite in NumPy.

### Failed: LangChain ConversationBufferWindowMemory for session history
Attempted. The idea was to store the last K messages in LangChain's `ConversationBufferWindowMemory`
and feed them back to the LLM on each turn. This worked for the first 2 turns. On turn 3,
when the memory contained tool-call messages (Action/Action Input/Observation), Groq's API
returned a 400 error: "Invalid request: tool_use blocks must be immediately followed by tool_result blocks."

This is a Groq-specific API constraint: tool-call history can't be arbitrarily inserted into
a new conversation context. The solution was to drop the full LangChain memory system entirely
and keep only a simple list of (question, answer) string pairs for display. The LLM reasoning
is always stateless — each turn is a fresh context.

### Failed: Sentence-transformer embeddings for the categorizer
Briefly attempted as an alternative to TF-IDF. The approach: encode all merchant names with
`all-MiniLM-L6-v2`, train a small linear layer on top. This was the "sentence-transformer
embeddings" option from Requirement 5.3. The problem: encoding 3000 merchant names with the
model took ~20 seconds on CPU, and storing the embedding matrix for 3000 training examples
added 3000 × 384 × 4 bytes = 4.6MB to the model artifact. The TF-IDF approach produces
a 75KB artifact. For a demo tool, artifact size matters. Abandoned.

### Failed: Using `pydantic-settings` for config
`pydantic-settings==2.14.2` is installed in the venv. The original `config.py` plan used
`class Settings(BaseSettings): ...` which auto-reads from environment. It was abandoned because:
1. `pydantic-settings` doesn't provide `sys.exit(1)` on missing required fields — it raises
   `ValidationError` which is a Pydantic exception, not a clean startup failure
2. The custom `Settings` class with `_validate_required()` calling `sys.exit(1)` is
   explicitly what the spec requires (Requirement 12.2: "exit with a non-zero exit code")
3. Adding `pydantic-settings` as a required dependency for functionality achievable with
   20 lines of stdlib code was unjustified

### Failed: Adding a `date_range` parameter to `calculate_total` tool
Attempted. The tool signature `calculate_total(query: str, start_date: Optional[str] = None, end_date: Optional[str] = None)` was tried. The issue: Groq's Llama 3.1 8B consistently
failed to generate correct ISO date strings for the parameters (it would generate `"last month"`
instead of `"2024-01-01"`). With a single `query: str` parameter, the LLM has more freedom.
The current `calculate_total` tool is deliberately limited to category-level aggregation
because date parsing in LLM tool parameters is unreliable with small models.

### Failed: Using `anomaly_score` for the dashboard anomaly table color gradient
This wasn't implemented (the dashboard doesn't exist yet) but was planned and will fail
given the score distribution. The design imagined a color gradient from white (score=0)
to red (score=1). With scores maxing at 0.068, the entire table would be nearly white.
The score normalization fix in Section 16 Step 6 of HANDOVER_DEEP_DIVE.md must happen
before any visualization of anomaly scores.

### Failed: Making `PDFParser` work on real bank PDFs
The fixture PDF (`sample_bank_statement.pdf`) was generated by reportlab with a proper
`Table` widget. Real bank PDFs from HDFC, SBI, ICICI (likely banks given the IST timezone)
typically use:
1. Scanned images (no text layer) — pdfplumber returns nothing
2. Text positioned to look like a table but with no table structure — pdfplumber returns
   no tables from `page.extract_tables()`
3. HTML-rendered PDFs converted to PDF — works but column detection is unreliable

The `PDFParser` is effectively a demo parser that works on properly-formatted PDFs.
Real bank PDFs will require a different approach (coordinate-based text extraction with
manual column detection, or OCR). This is a known limitation not documented anywhere.

## SECTION 6 — Unexpected Discoveries

### pdfplumber's table extraction requires actual table structure
Discovered when testing `no_transaction_table.pdf`. Expected: pdfplumber would extract
tabular-looking text regardless of structure. Reality: `page.extract_tables()` returns
only tables that have clear cell boundaries (lines or whitespace patterns that pdfplumber
detects as column separators). A PDF with right-aligned text in consistent columns —
the way most real bank PDFs look — returns empty from `extract_tables()`.
**This means the PDFParser is only useful for a narrow category of well-structured PDFs.**

### LangChain tool docstrings are part of the LLM's context
The `@tool` decorator uses the function's docstring as the tool description sent to the
LLM. The quality of the docstring directly affects whether the LLM calls the right tool.
The current `retrieve_transactions` docstring says "Use this to find relevant transactions
when answering questions about specific spending, merchants, or categories." — this is good.
But `calculate_total`'s docstring had to be carefully worded to prevent the LLM from calling
it for individual transaction lookups (which should use `retrieve_transactions`).

### sentence-transformers caches the model on first use
`SentenceTransformer("all-MiniLM-L6-v2")` downloads the model (~22MB) to
`~/.cache/huggingface/hub/` on first use. Subsequent instantiations load from cache.
This means **the first time `VectorStore()` is called on a fresh machine, it needs internet
access.** In offline environments, you need to pre-download the model and set
`TRANSFORMERS_OFFLINE=1`. This is not documented anywhere in the project.

### IsolationForest with `contamination="auto"` vs float
If `contamination` is set to `"auto"` (sklearn default in newer versions), IsolationForest
uses a threshold based on the original paper's scoring. With a float (0.05), it explicitly
marks the N% most isolated points as anomalies. The current implementation uses 0.05 (explicit).
This means EXACTLY 5% of transactions are always anomalies. With 200 transactions: exactly 10.
This is a feature during development (predictable test assertions) but a limitation in production
(real datasets may have 0% or 20% anomalies).

### NumPy `save` and `load` with `.npy` append
`np.save("file.npy", array)` always writes the whole array. There is no append mode.
This is why every `index()` call rewrites the entire file. FAISS has an `add()` method
that adds without rewriting — NumPy doesn't. This is fundamental and can't be worked
around without keeping the whole array in memory and only flushing to disk explicitly.

### pytest `tmp_path` is per-test, not per-session
This seems obvious but it caused subtle confusion: if test A creates a `TransactionStore`
in `tmp_path/test.db` and test B also creates one in `tmp_path/test.db`, they are in DIFFERENT
directories. `tmp_path` in pytest is unique per test function. Tests that expected to share
a database (e.g., "insert in fixture, query in test") would see empty stores. The correct
pattern is to use `tmp_path` in the test function itself and pass the path to the store.

### Groq API rate limits in practice
Free tier: 14,400 requests/day, 500,000 tokens/minute. In practice during development,
the chat endpoint was tested maybe 20 times total. Rate limiting was never hit. But if the
Streamlit dashboard is demo'd aggressively (many chat turns in quick succession), it could
hit the tokens/minute limit. The error from Groq is an HTTP 429 that LangChain surfaces
as a `RateLimitError`. `handle_parsing_errors=True` in AgentExecutor will catch this as a
"parsing error" and return a generic error message — not ideal. Add explicit rate limit
handling if the demo is going to be live.

### Windows path handling with Path vs string in SQLite
`sqlite3.connect(Path("data/processed/finsight.db"))` works on Python 3.12+. Earlier
Python versions required `sqlite3.connect(str(Path(...)))`. The current code always does
`sqlite3.connect(self.db_path)` where `db_path` is a string passed to `TransactionStore.__init__`.
This is safe. But don't pass a `Path` object directly if you're on Python < 3.12.

### The `source_file` column behavior with the ingest endpoint
When the API ingests a file, it sets `txn.source_file = filename` where `filename` is the
upload filename. This means re-uploading the same file (same name) correctly deduplicates.
But uploading a file with a different name that has the same transactions will insert
duplicates (because `source_file` is different in the uniqueness key). This is intentional
— if you rename a file, you get duplicate data. Users should be warned about this in the UI.

## SECTION 7 — Hidden Coupling

### The most dangerous hidden coupling: `PDFParser` → `CSVParser` private methods

`PDFParser` calls `self._field_mapper._canonical_field_name()`, `._parse_date()`,
and `._parse_amount()` — all private methods of `CSVParser`. If you rename any of these
methods in `CSVParser`, `PDFParser` silently breaks with `AttributeError` at runtime.
There is NO test that exercises the PDFParser path through CSVParser's private methods
in isolation. The PDF parser tests test end-to-end behavior; they don't test that the
alias mapping is applied via CSVParser specifically.

**Breakage scenario:** Rename `_parse_amount` to `_parse_numeric_amount` in `csv_parser.py`.
Run `pytest tests/unit/test_csv_parser.py` — all 12 pass. Run `pytest tests/unit/test_pdf_parser.py` — all 5 pass (because the test PDFs use "Debit" column which maps to "amount" via the alias, and the amount values are simple floats). The breakage would only appear on a PDF with a currency symbol or comma in the amount — a case not covered by the test fixtures.

---

### Hidden coupling: `VectorStore` text format → Agent retrieval quality

`VectorStore._transaction_text()` generates `"{merchant} {category} {amount} {date}"`.
The `retrieve_transactions` tool calls `vector_store.search(query, k=k)`. The semantic
similarity between the query and stored texts depends entirely on this format.

If you change the format to `"{category}: {merchant} on {date} for ${amount}"`, the
embedding space changes. Queries like "grocery shopping" would return different results
than with the current format. The VectorStore tests only check that the text CONTAINS
the right fields — not their order or format.

**Breakage scenario:** Changing the format would make existing stored embeddings
(`.npy` + `metadata.json`) inconsistent with newly indexed embeddings, since old entries
use the old format and new entries use the new format. Search results would be unreliable.
**Never change `_transaction_text()` without also deleting all existing embeddings and
re-indexing from scratch.**

---

### Hidden coupling: `Categorizer` label encoder → category string format

The `LabelEncoder` in the Categorizer is trained on the exact category strings from
`SyntheticGenerator` (e.g., `"Groceries"`, `"Dining"`, etc., with exact capitalization).
The label encoder is saved inside `categorizer.joblib`. If you change a category name
in `SyntheticGenerator` (e.g., `"Dining"` → `"Food & Dining"`), you must retrain the
model and update `CANONICAL_CATEGORIES` in `categorizer.py`.

But there's a subtler issue: `TransactionStore.query_by_category()` uses case-insensitive
matching. So `query_by_category("groceries")` works. But `Categorizer.predict()` returns
`"Groceries"` (capitalized). If you ever query by the predicted category using exact case,
it works. But if you later change the capitalization convention, the case-insensitive
SQLite query still works while explicit comparisons in Python code break.

---

### Hidden coupling: `AnomalyDetector` → `TransactionStore` `_get_connection()` private method

Covered in Section 4. The anomaly detector uses `store._get_connection()` directly to
update records. If `TransactionStore` changes from SQLite to PostgreSQL, or changes its
connection management (e.g., uses a connection pool), `AnomalyDetector.fit_and_score()`
breaks silently at runtime. There is no interface contract — it's pure implementation coupling.

---

### Hidden coupling: `app.py` hardcoded model path

```python
model_path = Path("data/processed/categorizer.joblib")
```
This is relative to the working directory, not to `__file__`. If you run uvicorn from
`src/` (`uvicorn main:app` from inside `src/`), the model path resolves to
`src/data/processed/categorizer.joblib` which doesn't exist. The API starts but
categorizer is silently not loaded (no error, just no categorization).

---

### Hidden coupling: `test_pdf_parser.py` → physical fixture files on disk

Unlike all other unit tests (which use `tmp_path` or inline data), `test_pdf_parser.py`
loads files from `tests/fixtures/`. These files exist on this machine but are NOT in git
(they're binary PDF files — wait, they ARE committed based on the git tree inspection).
Let me correct: the fixtures ARE committed (they're in `.gitignore`? No — they're in
`tests/fixtures/` which is not in `.gitignore`). They should be in git. If they're not
present on a fresh clone, all 5 PDF parser tests will fail with `FileNotFoundError`.
Run `python scripts/generate_pdf_fixtures.py` to regenerate them if missing.

---

### Hidden coupling: `conftest.py` path insertion → all test module imports

Every test file starts importing from `agent`, `categorization`, `anomaly`, etc. without
`src.` prefix. This works only because `conftest.py` at the project root inserts `src/`
into `sys.path`. If `conftest.py` is deleted, moved, or the path insertion is removed,
every single test file gets `ModuleNotFoundError`. There are NO relative imports in any
test file — they all use absolute imports that depend on this path hack.

## SECTION 8 — Mental Model: How I Think About This Architecture

### The whiteboard drawing order

If explaining this on a whiteboard, I would draw it in this exact order:

**1. Draw the Transaction box first, center of the board.**
`Transaction(date, merchant, amount, category, id, is_anomaly, anomaly_score, needs_review, source_file)`
Everything in the system is either producing, transforming, storing, or querying `Transaction`
objects. This is the invariant. Draw it as a rectangle, not a circle.

**2. Draw two arrows going INTO the Transaction box.**
Left arrow: "CSV/PDF → Parser → Transaction" (ingestion)
Right arrow: "Random → SyntheticGenerator → Transaction" (development data)
These are the only two ways Transaction objects are created. There is no third way.

**3. Draw the storage tier below Transaction.**
Two boxes: SQLite (TransactionStore) and NumPy files (VectorStore).
A thick arrow from Transaction to SQLite: "insert + deduplicate"
A thinner arrow from Transaction to VectorStore: "embed + index"
These two stores are supposed to be atomic (they're not — draw a red X on the arrow).

**4. Draw the enrichment layer above Transaction.**
Three boxes: Categorizer, AnomalyDetector, Forecaster.
Categorizer: reads `merchant`, writes `category` and `needs_review` (BEFORE storage)
AnomalyDetector: reads SQLite, writes `is_anomaly` and `anomaly_score` (AFTER storage)
Forecaster: reads SQLite, produces new ForecastPoint objects (no writes)

**5. Draw the API box at the top.**
FastAPI sits above everything, orchestrating the enrichment pipeline per request.
It calls: Parser → Categorizer → Store → VectorStore → AnomalyDetector (in this order)

**6. Draw the Agent to the right of FastAPI.**
Agent calls: VectorStore (retrieve), TransactionStore (total), Forecaster (forecast),
AnomalyDetector (anomalies). The agent READS but never WRITES.

**7. Draw the user entry points.**
Two entry points: File upload (left) → API → pipeline → stores
Natural language question (right) → API → Agent → tools → stores

**The mental model in one sentence:**
Files come in through parsers, get enriched by ML, land in two synchronized stores, and
the agent queries those stores to answer questions. The API orchestrates everything.

---

### What the architecture FEELS like to work in

- Adding a new parser (e.g., OFX format): just implement `parse(file_path) -> (list[Transaction], ParseSummary)` in a new file. Nothing else changes.
- Adding a new agent tool: add a `@tool` decorated function in `tools.py`, add it to the list returned by `create_tools()`. Nothing else changes.
- Adding a new API endpoint: add a function in `app.py`. Nothing else changes.
- Adding a new ML model: add a new module under `src/`, call it from the ingest pipeline in `app.py`. The Transaction dataclass already has fields for is_anomaly — for a NEW type of enrichment, you'd need to add a new field to Transaction AND update the SQLite schema.

The architecture is genuinely modular. The only coupling anxiety is around `domain.py` changes.

## SECTION 11 — Biggest Engineering Lessons

### Python lessons

**Lesson 1: `@dataclass` defaults that are mutable must use `field(default_factory=...)`**
`Transaction` has `anomaly_score: Optional[float] = None` — this is fine because `None`
is immutable. If you ever add a list field (e.g., `tags: list[str] = []`), it will be a
shared mutable default across all instances. Use `tags: list[str] = field(default_factory=list)`.
The current dataclass is safe — but anyone extending it needs to know this rule.

**Lesson 2: `utf-8-sig` encoding is mandatory for Windows Excel exports**
Any CSV exported from Excel on Windows will have a BOM prefix. `open(file, encoding='utf-8')`
will include `\ufeff` as the first character of the first header. `csv.DictReader` will
create a key named `'\ufeffdate'` instead of `'date'`. The fix is `encoding='utf-8-sig'`
which strips the BOM silently. This cost 2 hours to debug.

**Lesson 3: `sqlite3.Row` is worth the one extra line**
`conn.row_factory = sqlite3.Row` enables named column access. It's easy to skip for
"simple" projects. Don't. Without it, `row[0]`, `row[1]` etc. create fragile code that
breaks when column order changes.

**Lesson 4: Python `random.Random(seed)` vs `random.seed(seed)`**
`SyntheticGenerator` uses `rng = random.Random(seed)` — a separate Random instance per
call, not the global random state. This is critical for determinism: `random.seed(seed)`
affects the global state which could be modified by any library. Using `random.Random(seed)`
gives a fully isolated RNG that produces identical output regardless of what other code
has called the global `random` module. This was a deliberate choice.

---

### ML lessons

**Lesson 1: F1=1.0 is a red flag, not a success**
When you see F1=1.0 on a classification task, your first thought should be "what's wrong
with the evaluation?" The categorizer achieves F1=1.0 because training data and test
data come from the same 44-merchant vocabulary. Real-world accuracy is 30–40%. Always
evaluate ML models on genuinely held-out data that differs structurally from training data.

**Lesson 2: Anomaly score normalization needs per-batch calibration**
`clip(-decision_function, 0, 1)` sounds correct but produces near-zero values because
IsolationForest's `decision_function` outputs are in [-0.2, 0.2] range, not [-1, 1].
The fix (min-max normalization per batch) is simple but must be done. Always inspect
the actual distribution of scores before considering a normalization formula "correct."

**Lesson 3: Prophet is installation-hostile on Windows**
Prophet requires CmdStan (a C++ program) for Bayesian inference. On Windows, this
requires Visual Studio Build Tools or MinGW. The install experience is fragile and
version-sensitive. For any project targeting developers across platforms, having a
"simple numpy alternative" is worth the accuracy tradeoff.

**Lesson 4: TF-IDF character n-grams are surprisingly good for merchant names**
`analyzer='char_wb', ngram_range=(2,4)` extracts 2-4 character substrings from merchant
names. "CVS Pharm" → "CV", "VS", "S ", " P", "Ph", "ha", etc. These substrings are
distinctive per category. "Pharm" substrings appear in Healthcare merchants. "Foods"
substrings appear in Grocery merchants. The model essentially does substring pattern
matching. It fails completely on new merchant names with no training-set substrings.

---

### API lessons

**Lesson 1: FastAPI's `Depends` exists for a reason**
The `_get_components()` anti-pattern was written in 30 minutes. The proper `Depends`
pattern would take 2 hours to set up correctly with `lifespan`. Both work functionally
in development. But the `Depends` pattern is the one you'll thank yourself for when
writing tests, adding authentication middleware, or handling startup failures gracefully.
Never compromise on DI patterns — they're the most expensive shortcuts to undo.

**Lesson 2: Always use `lifespan` for startup/shutdown**
`@app.on_event("startup")` was deprecated in FastAPI 0.93+. The correct pattern is
the `lifespan` context manager. More importantly: startup code in `lifespan` runs BEFORE
the server accepts requests, so a startup failure (missing model file, wrong API key)
prevents the server from starting cleanly. Deferred initialization (`_get_components()`)
means the server appears healthy but individual requests fail.

---

### LangChain/RAG lessons

**Lesson 1: Tool docstrings are the most impactful thing you can tune**
The LLM reads the tool docstring to decide which tool to call. A vague docstring
("gets transactions") leads to wrong tool selection. A specific docstring with examples
("Use this when the user asks about total spending in a category or overall") leads
to correct tool selection. The docstrings in `tools.py` were revised multiple times.

**Lesson 2: Small models don't handle multi-turn tool-call history**
Llama 3.1 8B cannot reliably replay tool-call history in subsequent conversation turns.
This is a fundamental limitation of smaller models — they confuse historical tool calls
with new instructions. The stateless-per-turn design in `agent.py` is the correct
workaround, not a hack. Larger models (GPT-4, Claude 3) handle this better.

**Lesson 3: `max_iterations=3` is a safety net, not a feature**
Setting `max_iterations=3` prevents infinite loops where the LLM keeps calling tools
without producing a final answer. If you increase it, you risk runaway API costs. If
you decrease it to 1 or 2, complex questions that genuinely need 3 tool calls will
produce incomplete answers. 3 is the right number for a 4-tool single-domain agent.

---

### Testing lessons

**Lesson 1: Tests that pass for the wrong reason are worse than no tests**
`test_predict_batch_handles_individual_errors_without_aborting` wraps its assertion in
`try/except RuntimeError`. If the tested behavior is broken, the exception propagates
to the except block and the assertion never runs — the test passes silently. A test that
can never fail is actively harmful: it gives false confidence and hides regressions.

**Lesson 2: Use `tmp_path` for everything file-related in tests**
Every test that touches the filesystem should use pytest's `tmp_path` fixture. Hardcoded
paths in tests create cross-contamination between test runs and make parallel execution
impossible. The codebase follows this correctly except for `test_pdf_parser.py` which
reads from `tests/fixtures/` — but fixture files are immutable so this is acceptable.

**Lesson 3: The `vector` marker was the right call**
Without `pytestmark = pytest.mark.vector`, the sentence-transformer tests would either
slow down every test run (by loading a 22MB model) or cause DLL failures on Windows.
Having a marker allows `pytest -m "not vector"` for fast development iteration. Any
time you have a test that requires heavy dependencies (models, databases, network),
give it a marker.

## SECTION 12 — Hidden Assumptions Not Documented Elsewhere

These are the ones that didn't make it into PROJECT_STATUS.md or HANDOVER_DEEP_DIVE.md:

1. **The `test_statement.csv` in `data/raw/` is the de facto integration test fixture.**
   It's 200 rows of clean synthetic data with canonical column names and all 8 categories.
   It was used for the manual API test that populated the live database. It's gitignored
   (lives in `data/raw/`) which means it won't exist on a fresh clone. Any integration
   test that uses it must either regenerate it or use a committed copy in `tests/fixtures/`.

2. **The VectorStore uses `transaction.id` as the deduplication key.**
   `_find_index()` searches by `transaction_id` in metadata. This means if a transaction
   is inserted into SQLite (gets an `id`), then `vector_store.index(txn)` is called, the
   embedding is keyed by that `id`. If the transaction is deleted from SQLite and a new
   transaction gets the same auto-increment `id` (which SQLite does NOT guarantee — it
   picks the max+1), the vector store would upsert the wrong embedding. In practice with
   SQLite's AUTOINCREMENT behavior, IDs are never reused, so this is safe.

3. **`app.py` indexes ALL transactions after every ingest, not just new ones.**
   Line in `app.py`: `for txn in all_txns: vector_store.index(txn)`.
   `all_txns = store.get_all()` returns EVERYTHING in the database. On the first ingest
   (200 rows), this calls `encode()` 200 times. On the second ingest (another 50 rows),
   it calls `encode()` 250 times. On the Nth ingest, it's O(total × new) not O(new).
   This will become visibly slow after 1000 total transactions.

4. **The `SentenceTransformer` model is loaded with default trust settings.**
   `SentenceTransformer("all-MiniLM-L6-v2")` downloads from HuggingFace Hub without
   `trust_remote_code=True`. This is correct and safe for this specific model. But if
   someone changes the model name to a custom or third-party model, they need to understand
   the trust implications.

5. **The `Forecaster` fails gracefully for categories with < 14 days but `forecast_all()`
   converts these failures to strings.**
   The dashboard code must check `isinstance(result, Forecast)` before trying to access
   `result.points`. If it accesses `.points` on an error string, it gets `AttributeError`.
   This is a silent runtime failure that would show a broken chart instead of a message.

6. **Groq's `llama-3.1-8b-instant` is a specific model ID, not a version alias.**
   If Groq renames, deprecates, or removes this model, the `/chat` endpoint fails with a
   404 or 422 from Groq's API. There is no fallback model. The model name is hardcoded
   in `agent.py` with no config option.

7. **The `source_file` field is set by the API (`txn.source_file = filename`) not by parsers.**
   `CSVParser.parse()` returns transactions with `source_file=""` (the dataclass default).
   The API sets it after parsing. This means any code that calls the parser directly
   (e.g., scripts or tests) will have transactions with empty `source_file`. The
   deduplication key `(date, merchant, amount, source_file)` then treats all such
   transactions as coming from the same unnamed source. Two separate scripts ingesting
   the same data would deduplicate correctly. Two separate scripts ingesting different
   data with the same amounts would also deduplicate incorrectly.

8. **The `needs_review` column in SQLite is never queried by the API.**
   `TransactionStore` stores `needs_review` in the schema. `TransactionDTO` includes it.
   But no API endpoint specifically filters or surfaces `needs_review=True` transactions.
   The flag is stored, returned in all transaction responses, but there's no
   "show me transactions that need review" endpoint. This is a missing feature.

## SECTION 13 — Things ChatGPT Should Never Accidentally Break

(Beyond what's in HANDOVER_DEEP_DIVE.md Section 17 — these are the remaining ones)

**`src/ingestion/transaction_store.py` — `_init_schema()` idempotency**
`CREATE TABLE IF NOT EXISTS` and `CREATE UNIQUE INDEX IF NOT EXISTS` are both idempotent.
If you add a new column and change them to `CREATE TABLE`, you'll wipe the existing
database on the first API request. Always keep the `IF NOT EXISTS` clauses.

**`src/api/models.py` — `IngestResponse` has `warnings: list[str] = []`**
The default empty list means `warnings` is optional in responses. If you remove the
default, the Pydantic model will require `warnings` to be explicitly provided in every
`IngestResponse(...)` call. There are exactly 1 call site in `app.py`. Easy to miss
if the default is removed.

**`src/agent/tools.py` — `@tool` decorator captures variables by closure**
All four tools are defined as inner functions inside `create_tools(store, vector_store, ...)`.
They capture `store`, `vector_store`, `forecaster`, `anomaly_detector` from the enclosing
scope. If you move the tool definitions outside of `create_tools()` (to make them easier
to test), they lose access to these objects and must receive them as parameters — which
breaks the `@tool` decorator pattern (LangChain tools can't have injected parameters).

**`tests/unit/test_config.py` — `@pytest.fixture(autouse=True)` singleton reset**
Every test function in `test_config.py` gets the singleton reset before and after via
`config.reset_settings()`. If you add new tests to `test_config.py` without understanding
this fixture, your tests may see stale settings from previous tests.

**`src/ingestion/pretty_printer.py` — exact field order**
`CANONICAL_FIELDS = ("date", "merchant", "amount", "category")`. The round-trip test
verifies that CSVParser can re-parse PrettyPrinter output. If you change the field order
in `to_csv_string()` (even to alphabetical), the round-trip test still passes but any
external tool expecting `date,merchant,amount,category` header order breaks.

## SECTION 14 — Developer Advice: Things That Save Hours

### Debugging tips

**When the API seems to "not categorize" transactions:**
The categorizer only runs if `categorizer._is_trained` is True. Check if
`data/processed/categorizer.joblib` exists. If not, run `python scripts/train_categorizer.py`.

**When `pytest tests/unit/` hangs for 60+ seconds:**
You accidentally included `test_vector_store.py`. This test tries to load SentenceTransformer
which on Windows takes 60+ seconds before hitting the DLL error. Always use:
`pytest tests/unit/ --ignore=tests/unit/test_vector_store.py`

**When the API returns 200 but chat gives error about agent:**
The `LLM_API_KEY` in `.env` may be expired or invalid. Test with:
`curl -X POST http://localhost:8000/chat -H "Content-Type: application/json" -d "{\"message\":\"how much did I spend?\",\"session_id\":\"test\"}`
A Groq API error will appear in the response's `answer` field.

**When ingest seems slow (30+ seconds per request):**
The VectorStore is re-indexing ALL transactions on every ingest (not just new ones).
With 200 transactions, 200 encode calls take ~15 seconds on CPU. This is by design
but is the biggest latency source. Fix: only index newly inserted transactions.

**When `import domain` fails in a script or notebook:**
You need `sys.path.insert(0, "src")` before any project imports. Check how
`scripts/train_categorizer.py` does it at lines 5-6.

### Implementation tips

**When adding a new endpoint to `app.py`:**
1. Define the Pydantic response model in `models.py` first
2. Write the unit test that will validate the endpoint behavior
3. Only then write the endpoint handler
4. Test with `TestClient` before running uvicorn

**When adding a new agent tool:**
1. Write it in `tools.py` inside `create_tools()`
2. Add it to the `return [...]` list at the bottom

**The `anomaly_score` in the live database is effectively zero for all transactions:**
Confirmed by direct query: anomalies have scores in [0.00006, 0.068]. The `is_anomaly`

**The Forecaster `alpha=0.3` produces very smooth, conservative forecasts:**
EWMA with α=0.3 puts 30% weight on the most recent observation and 70% on the
historical average. For a user who just changed their spending habits (e.g., started
spending more on Dining after a lifestyle change), the forecast will lag by weeks.
A higher α (0.5–0.7) would be more responsive. Consider making this configurable.

**Why the agent prompt says "Do not call the same tool twice for the same question":**
During testing, Groq's Llama 3.1 8B would call `retrieve_transactions` twice in a row
for the same query — once to "find" the data and once to "confirm" it. This doubled
latency and sometimes returned contradictory results. The prompt instruction reduces
this behavior to ~10% of cases.

**The `max_length=2000` on ChatRequest.message is the only DoS protection:**
There is no rate limiting. A malicious user could send 2000-character messages to `/chat`
repeatedly, consuming both server CPU and Groq API credits. The only mitigation is the
message length cap. For a local single-user tool this is acceptable; for any public
deployment, add rate limiting.

**Why `conftest.py` inserts at index 0, not appending:**
`sys.path.insert(0, str(Path(__file__).parent / "src"))` puts `src/` at the FRONT of
the path. This ensures that if there's any globally installed package with the same name
as a project module (e.g., a global `domain` package), the project's version wins.
Appending (`sys.path.append`) would risk picking up the wrong module.

**The `needs_review` flag from the categorizer is stored but never surfaced to the user:**
Transactions with `needs_review=True` have their categories set to "Other" by the
categorizer. These are transactions where the model wasn't confident. There's no API
endpoint to filter by `needs_review=True` and no dashboard panel showing them. This is
a high-value feature gap: users should see "these N transactions need you to manually
set the category." A `GET /transactions?needs_review=true` filter and a dashboard
"Review Queue" tab would significantly improve the product.

**The `VectorStore` will silently corrupt if `.npy` and `.json` get out of sync:**
If the process is killed between `np.save(npy)` and `json.dump(metadata)` in `_save()`,
the two files will be inconsistent (more embeddings than metadata or vice versa). The
`_load()` method doesn't validate consistency — it just loads both and trusts them.
A defensive `assert len(self._embeddings) == len(self._metadata)` in `_load()` would
catch corruption early.

**The `IsolationForest` is re-fit from scratch on every ingest:**
If you have 10,000 transactions and ingest 1 new one, the anomaly detector re-trains on
all 10,001 transactions. IsolationForest doesn't support incremental training (`partial_fit`).
The only way to avoid this is to only re-fit periodically (e.g., after every 100 new
transactions) rather than after every ingest. Add a configurable `refit_threshold` to
`AnomalyDetector`.

**The database file path is stored as a string from `Settings.SQLITE_DB_PATH`:**
`TransactionStore.__init__` takes `db_path: str`. If `SQLITE_DB_PATH` is a relative
path like `data/processed/finsight.db`, the database is created relative to the current
working directory. On a fresh clone, if `data/processed/` doesn't exist, `TransactionStore.__init__`
calls `Path(db_path).parent.mkdir(parents=True, exist_ok=True)` — which creates the directory.
This is safe and correct.

`src/api/models.py` and `VectorStore` is in `src/api/vector_store.py`. These exports
exist because `app.py` imports from `api.models` directly — the `__init__.py` re-exports
are never actually used by anything in the project. They're dead re-exports that could
be removed without consequence.
